<p class="dropcap">On Tuesday, October 20, 2026, two PHP vulnerabilities leaked ahead of the scheduled coordinated disclosure. PHP runs about 70% of websites, by W3Techs' count. The vulnerabilities were CVE-2026-109618 and CVE-2026-109619, together known as PHP2Shell. Both are remote code execution vulnerabilities, or RCE. An attacker can use either one to run their own commands on your server without a password. The PHP project said fixed versions would ship the next day at 14:00 UTC. Security vendors were already reporting attack attempts.</p>

I run several servers for <Redacted size="l" />. One of them had two internet-facing services that use PHP. Both were on fixed PHP a little over nine hours after I started, and an allow-list at the reverse proxy covered most of the time before that.

## Incident Scope

Two services on the host ran PHP and faced the internet. <Redacted /> is the self-hosted control plane that deploys every other app on the host, and anyone on the internet could reach its PHP login page. The other was a project-management app behind single sign-on (SSO), except for one API route that bypassed it.

The control plane was the highest risk. It has the Docker socket, the host's SSH keys and the secrets of every app it deploys. Exploiting PHP2Shell against the control plane would give full control of the server. Code execution in the project app would give an attacker that app, its database and a foothold on the internal network.

PHP patches had not yet shipped. The prevailing advice on Reddit and Hacker News was to turn off session upload progress in PHP and to limit file uploads. I turned off upload progress at 11:24, after the allow-list was already up.

## Containment

The allow-list mitigated most of the risk. It took about ten minutes, needed no patch and no restart, and stopped every request from an unknown address before it reached PHP.

I use Traefik as my reverse proxy. Traefik reads extra rules from files and picks them up without a restart, which is what made this a ten-minute fix. I left the existing routes alone and added one new file. It matches the same hostname at a higher priority, so its rules are checked first, and it puts an allow-list in front of the dashboard. Here is the pattern, with documentation addresses and an example domain:

<div class="code-cap"><span>Traefik dynamic configuration (example)</span><span>YAML</span></div>

```yaml
# Matches the dashboard's hostname at a higher priority than the existing
# routes, so these rules win. Unknown sources get 403 before PHP runs.
http:
  middlewares:
    admin-only:
      ipAllowList:
        sourceRange:
          - 198.51.100.7/32   # my workstation
    github-hooks:
      ipAllowList:
        sourceRange:
          # Stand-ins: copy the real "hooks" ranges from api.github.com/meta.
          - 192.0.2.0/26
          - 203.0.113.64/27

  routers:
    dashboard-guard:
      rule: Host(`deploy.example.com`)
      priority: 2000
      entryPoints: [https]
      middlewares: [admin-only]
      service: dashboard@docker
      tls: {}
    github-webhooks:
      rule: Host(`deploy.example.com`) && PathPrefix(`/webhooks/github/`)
      priority: 2100
      entryPoints: [https]
      middlewares: [github-hooks]
      service: dashboard@docker
      tls: {}
```

### Allow-List Checks

1. Confirm the proxy sees the real client address. If it only sees an internal address, an allow-list lets in everyone or no one. My workstation's single address matched, which proved the real addresses arrived.
2. Give webhooks from your Git server and from GitHub their own routes. GitHub publishes its webhook source ranges at `api.github.com/meta`. Copy them when you write the rule, and refresh them later.
3. If your own address changes, the dashboard answers 403 to you too. Know how to reach the server another way, and which line to edit.
4. Test from the allowed address, from a refused one and from each webhook source, and test again after every upgrade.

## User Notification

The same day I also sent a short notice to the people who use these services. It told them they were safe, that they did not need to do anything, and to expect scam emails. Here it is, lightly edited for this page.

<Pull label="The notice, October 21, 2026" caption="Sources given with the notice: the PHP project and W3Techs.">

On October 20, details leaked about a serious flaw in PHP. PHP is software that runs most of the websites in the world. The flaw lets attackers take control of a website without a password, and attacks have already started.

The services you use are safe. Your portal, chat and sign-in do not use PHP. I closed my two internal PHP tools to the internet within hours, and I found no sign of misuse. You do not have to do anything.

The rest of the internet is at risk. Many stores, blogs and other sites that you use will be slow to install the fix. Attackers will steal data from them and use it in fake emails.

To stay safe:

1. Do not click links in unexpected "security update" or "reset your password" emails.
2. Use a different password for each account, and turn on two-step sign-in.
3. If you own a website, ask your web host if it uses PHP and has the October 21 fix.

I will never ask for your password or send you a link to fix this. If a message from me looks wrong, call the number that you already have for me.

</Pull>

I left out version numbers, the list of systems and any promise that nothing can go wrong. Most readers only need to know whether they have to act, and the second paragraph answers that. The rest prepares them for the scam emails, which will reach far more of them than the flaw itself.

## Conclusion

The proxy allow-list covered both services from about 11:20 until their patched builds went live at 17:52 and 20:24, and it is still in place. The 17:52 upgrade renamed an internal service and broke one of its rules, and the retest at 18:16 caught it.
